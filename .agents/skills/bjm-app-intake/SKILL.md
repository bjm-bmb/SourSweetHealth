# App 需求受理与任务卡起草

需求方只需提供简要的概要需求（一句话、一段话或几个要点）。本流程由 Agent 完成分析、起草和填写任务卡，需求方只负责确认或提出修改，确认后任务卡冻结并进入 `bjm-app-delivery` 闭环。

任务卡结构以 `docs/agent-framework/task-template.md` 为唯一权威，字段不增不减；本技能只改变填写方式：由 Agent 起草、需求方确认，替代需求方手工填卡。

## 适用与边界

- 仅在需求方给出简要需求且尚无对应任务卡时使用；已有已确认任务卡的直接走 `bjm-app-delivery`。
- 起草期间主 Agent 只能新建/修改本任务的 `docs/agent-framework/tasks/APP-xxx-短名称.md`，不触碰 App 代码、构建脚本与其它文档。
- 未经需求方明确确认，不得进入规划、开发或构建验证；需求方确认前任务卡状态保持「草稿」。
- 需求方仍可选择手工复制模板填卡的旧路径，两条路径产出的任务卡地位相同。

## 受理流程

1. **只读分析**。主 Agent 将简要需求交给 `app_planner`（需求受理模式）。planner 结合目标项目既有代码、文档与 `docs/android/` 工程规范只读分析，产出任务卡草案的全部字段内容：任务类型判定（`feature` / `bugfix` / `refactor`）、目标与范围、实现要点（页面与导航、数据与状态、涉及文件、依赖与工程配置变更）、验收条件（Given/When/Then 由 planner 起草）、构建验证命令、显式不做清单。无法从简要需求与既有代码确定的字段，给出建议值并标注 `【待确认】`，不得编造后不加标记。
2. **编号与写卡**。主 Agent 扫描 `docs/agent-framework/tasks/` 目录，取现有最大 APP 编号 +1（三位数字，如 `APP-001`），从需求概括生成短名称，按 `task-template.md` 结构写入 `tasks/APP-xxx-短名称.md`，状态为「草稿」。
3. **确认轮**。主 Agent 向需求方展示任务卡全文，并单独列出待确认项清单（字段 + 建议值 + 依据）。需求方可「确认 / 提出修改 / 补充信息」；主 Agent 按反馈更新任务卡并再次展示，直至需求方明确确认。
4. **冻结**。需求方确认后：清除全部 `【待确认】` 标记，状态改为「已确认」，把确认方式与日期写入「需求依据」字段。此后任务卡内容即为本轮冻结的需求快照。
5. **交接闭环**。主 Agent 按 `bjm-app-delivery` 继续执行规划、开发、独立评审与修复复评。闭环中发现需求本身有空白或矛盾时，返回本流程第 3 步与需求方确认，不猜测。

## 起草规则

- 页面结构、数据来源、状态流转等技术细节由 planner 依据目标项目既有代码与 `docs/android/` 规范推断起草；推断要有出处，不得凭空编造。
- 验收条件一律由 Agent 起草为 Given/When/Then 格式，需求方只需确认是否符合预期。
- 「显式不做清单」必须起草：把概要需求未提及但容易过度发挥的页面、接口、第三方依赖与配置项列入，防止开发阶段扩范围。
- 构建验证命令默认 `.\gradlew.bat testDebugUnitTest assembleDebug`（Windows），项目另有约定时在任务卡中显式改写。
- 真机验证：任务卡必须写明是否需要（默认：涉及界面、导航、权限、启动流程的变化为「需要」），命令默认 `powershell -ExecutionPolicy Bypass -File tools\device_test.ps1 -ProjectDir .`，需要页面级断言时在任务卡「依赖变更」列出 androidTest 依赖。
- 安全边界章节按模板默认内容填写，不得删减。

## 最终交付物

任务卡文件路径与编号、任务类型判定及依据、待确认项的处理结果（每项的最终取值与来源）、需求方确认记录、进入闭环所需的冻结状态说明。
