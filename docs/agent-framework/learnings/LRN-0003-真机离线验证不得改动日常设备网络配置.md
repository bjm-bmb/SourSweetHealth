## 观察

评审为了截取「思考中 / 加载态」等需要网络挂起或失败的界面，直接在用户日常使用的手机上临时修改私有 DNS、HTTP 代理、防火墙等系统网络配置。虽然评审结束后恢复了配置，但修改期间应用真实地记录了域名解析失败，用户看到功能报错并误判为本次改动引入的回归，直接影响了交付信任。

## 证据

APP-001 第二轮评审使用「离线 / DNS 黑洞」保持思考态；同期真机上的应用对话记录出现 `UnknownHostException`（域名无法解析）。恢复网络后，`ping` 正常解析、应用发消息成功、设置页「测试连接」返回成功（336ms）。用户明确反馈「之前网络都是通的，你反而搞不通了」。

## 建议沉淀

在 `bjm-app-device-test` 增加硬性约束：不得在用户日常设备上修改系统网络配置（私有 DNS、HTTP 代理、防火墙、飞行模式、Wi-Fi/移动数据开关）。需要离线、超时或失败态时，优先使用（a）应用内可注入的 mock/延迟，（b）独立测试设备或模拟器，（c）仅在该任务专用设备上操作。若确需修改，必须事先征得用户同意，并在测试后逐项恢复，再用 `ping`/接口请求与设置页连接测试验证恢复结果。`docs/agent-framework/roles/app-reviewer.md` 同步「真机环境改动与恢复」清单，评审报告须记录改了什么、如何恢复、恢复验证结果。
