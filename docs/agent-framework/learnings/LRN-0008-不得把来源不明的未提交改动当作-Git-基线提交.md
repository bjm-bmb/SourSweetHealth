## 观察

为创建隔离 worktree，发现目标项目工作区存在大量未提交改动（含 UI 主题/配色重构）。需求方在上一轮明确表示「我没有 UI 改动」。执行 Agent 判断这些改动来自更早的 Agent 会话，于是将其作为一个「基线」提交并入主线，以便任务分支基于最新代码开发。

结果：该批改动从未经需求方确认，且其中包含破坏性缺陷（全局配色被替换、对话框形状被改成胶囊）。后续任务在这个坏基线上构建、评审并安装到真机，需求方直接看到被改坏的界面，导致交付返工。

## 证据

- APP-002：真机复现设置对话框被渲染成胶囊且标题被裁切；需求方反馈配色变丑。
- 回退提交后重新构建（`testDebugUnitTest assembleDebug` 退出码 0）并真机截图确认恢复。
- 根因可追溯到被当作基线提交的那批未提交改动中的自定义 `Shapes.extraLarge = RoundedCornerShape(percent = 50)` 与整组配色替换。

## 建议沉淀

在 `bjm-app-delivery`（及 `bjm-app-intake`）中增加硬规则：

1. 创建任务 worktree 前，若工作区存在未提交改动，**必须先获得需求方对这些改动归属与处理方式的明确答复**（提交为基线 / 另存 / 保持原样）。
2. 需求方声明「我没有改过某类文件」时，**不得自行推断来源后提交**；应报告差异清单（文件、行数、时间戳）并要求确认，或改用不依赖该基线的交付方式（例如在现有工作区交付并明确说明）。
3. 「基线提交」的提交信息不得描述为需求已确认；必须写明「未经需求确认的既有工作区状态」。
4. 涉及 UI 主题、Shapes、Typography、配色 token 的改动，即使只是「搬运既有改动」，也必须先在真机上看过截图再进入主线。

可机械判定的部分：可在交付流程检查中要求 handoff 提交的父提交与任务分支分叉点之间存在「基线提交」时，附带需求方确认记录。
