## 观察

一个「修复自动推送内容重复」的 bugfix 任务，最终在真机上同时改坏了三处与需求无关的地方：设置页的对话框形状与配色、列表加载时的滚动行为、首屏最后一条被输入栏遮挡。构建、单元测试与冒烟真机检查全部通过，问题全部由需求方手点发现。

复盘出两类越界：

1. **准备阶段越界**：把工作区里来源不明、需求方否认曾修改过的未提交改动当作「基线」提交进主线，等于替需求方决定了一批未经确认的界面变更。
2. **实现阶段缺乏范围机检**：任务卡写了「允许修改」，但没有任何机械手段验证实际 diff 是否落在该范围内；开发与评审都靠自觉阅读 diff。

需求方的评价是「依从性不够」：原本没有问题的功能被顺手改坏，比不做更糟。

## 证据

- APP-002：三个回归问题均可在 `git diff` 中定位到任务卡范围之外的文件。
- 新增 `tools/scope_check.py` 与 `tools/tests/test_scope_check.py`（8 个用例），在项目内对任务卡「允许修改」与 `git diff --name-only` 做机械比对：越界退出码 1。
- 在 `task-template.md` 增加「允许修改」必须写完整相对路径的硬要求（否则 scope_check 解析不到），并在「构建验证」中加入该命令。

## 建议沉淀

1. `bjm-app-delivery`、`bjm-app-intake`：任务卡「允许修改」必须逐条写完整仓库相对路径或目录前缀，供机检解析。
2. 开发与评审的完成标准都必须包含 `python tools/scope_check.py --task <任务卡> --since <基线 SHA>` 退出码 0；越界一律不允许以「顺手修复」为由通过。
3. 准备阶段发现工作区不干净时，必须列出差异并请求需求方确认，禁止擅自提交为基线（与 LRN-0008 配套）。
4. 评审检查清单新增「未改动区域回归」：逐项对照「明确不修改」，用 `git diff --name-only` 确认未被触碰。
