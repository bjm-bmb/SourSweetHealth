## 观察

真机验证脚本长期只做「安装 → 启动 → 进程存活 → 无崩溃」的冒烟检查。对于界面类改动，这组检查全部通过也可能是彻底错误的界面：对话框形状变成椭圆并裁字、配色与既有风格不符、设置项点击后没有保存、列表首屏从顶部滚到底部。这些缺陷编译不报错、单测覆盖不到、冒烟也发现不了。

评审清单里虽然有「UI 审美」「真机证据」条目，但缺少可执行的断言手段，实际上退化为「看一眼截图」。

## 证据

- APP-002：`device_test.ps1` 退出码 0、`app_check.py` 0 ERROR/0 WARN、18 个单测全绿的前提下，需求方在真机上发现三个界面缺陷。
- 本次为 `tools/device_test.ps1` 增加 `-UiSteps`（`tap:` / `assert:` / `wait:` / `shot:`），自动按 uiautomator 文本定位控件、点击、逐步截图并断言关键文本；实测
  `-UiSteps "tap:设置;assert:自动涌现;tap:自动涌现;assert:每天早上 6 点;shot:surge-dialog"`
  通过并产出 `step-*.png`；断言不存在文本时正确返回退出码 1 并保留失败截图。
- `tools/app_check.py` 同时新增 `shapes-capsule`（ERROR）、`settings-write-scope` / `chat-list-reverse`（WARN）三条 Compose 回归规则，把可机械判定的部分前移。

## 建议沉淀

1. `bjm-app-device-test` 与 `docs/android/device-test-automation.md`：界面改动必须提供 `-UiSteps`，未提供时结果记 SKIP 且不得作为验收证据。
2. `task-template.md`：新增「交互必点路径」字段，与构建/真机验证并列。
3. `review-checklist.md`：新增「交互级真机复核」与「未改动区域回归」两条人工项，明确冒烟 PASS 不构成界面验收证据。
4. 首屏类改动要求 300ms 连拍确认「第一次可见帧即目标状态」；设置项类改动要求读取应用私有存储确认落盘。
5. 后续可把 `-UiSteps` 的常用路径（设置页、自动涌现、主题详情）固化为项目内脚本，降低每次手写成本。
